# Decisions

Short records of the choices that shape Gutter, and why. Newest last. Change a decision by adding a new entry, not by editing an old one.

## 1. Comprehension, not review

Gutter does not find bugs, suggest fixes, or comment line-by-line. CodeRabbit, Greptile, Graphite and GitHub Copilot review compete there with large funding and platform position. The open space is upstream of judgment: helping a human build the right mental model of a change before reading the diff. Code-review research supports the premise (reviewers start by building context; alphabetical file order fragments it). Boundary: **we explain; others judge.** Any feature that drifts into verdicts needs a new decision here first.

## 2. Repo Archaeology is the statistics engine; Gutter consumes its v1 JSON

Gutter shells out to `repo-archaeology diff --json` and `backtest --json` and maps the result. It does not mine history itself. Benefits: one tested implementation of co-change, Wilson ranking, sweep filtering and rename following; Repo Archaeology stays independently useful; Gutter stays zero-dependency. Cost: an `npx` call per run, removable once Repo Archaeology exports a library API (see roadmap).

## 3. `gutter.json` is the product

Analysis writes one evidence document; renderers only read it. This keeps the comic page swappable (so it can be A/B tested against a plain layout with identical evidence), and lets future surfaces (IDE, agent skill, analytics) reuse it. Invariant enforced in code: every checklist item cites evidence ids that exist in the document.

## 4. Deterministic by default

No LLM in the pipeline. Every sentence is a template over counted facts. If narration is added later, it reads only `gutter.json`, and the evidence wins any conflict. This also keeps margins and the privacy story simple: no code leaves the runner.

## 5. Quiet is the default success state

Salience levels: `quiet` (one line, and no new comment in `auto` mode), `brief`, `full`. The checklist is capped at 4. Weak companions (Wilson lower bound < 30%) and companions backed mostly by bot commits appear in the evidence table but never become questions. AI-review studies show high rejection rates for noisy comments; trust is spent fast and earned slowly.

## 6. Calibration is shown on every brief, and it gates questions

Each run replays Repo Archaeology's backtest on held-out recent history and prints the result in plain words. When measured precision falls below 25%, co-change questions are suppressed for that repo, while the evidence still shows. "Lift" uses Repo Archaeology's own definition (hit rate vs. a popularity baseline on the same changes) so the two tools never print different multipliers for the same repo.

## 7. Two renderers: compact Markdown in the PR, comic page as an artifact

PR comments can't render custom HTML/CSS. The comment is compact Markdown with collapsible sections; the comic page ships as a workflow artifact (and locally as `gutter.html`). A later GitHub App can render the page to PNG for inline display. The comic is the distribution loop and the memorable artifact. The value sits in the evidence, so the compact mode must stand on its own.

## 8. Security posture

`pull_request` only, never `pull_request_target`. Fork PRs fall back to summary + artifact. All PR-derived text is escaped per output format; links come only from `http(s)` bases and hex SHAs; git runs via argument vectors. Gutter never fails a build. An analysis error becomes a warning annotation.

## 9. Zero runtime dependencies; Node ≥ 22

Published builds and release tags ship compiled ES2022 JavaScript in `dist/`, which runs on Node.js ≥ 22 (`engines.node: ">=22"`) without experimental flags or runtime dependencies — matching `repo-archaeology@^0.3.0`'s Node ≥ 22 requirement while Node 20 is EOL. Local development (`npm run dev`) and tests (`npm test`) run `.ts` sources directly via Node ≥ 22.6 type stripping (`--experimental-strip-types`), `node:test` for tests, and `parseArgs` for the CLI. Smaller attack surface for something that runs in other people's CI.

## 10. Free Action first; paid GitHub App later

The CLI and Action stay free and MIT. Monetization, if any, is a companion GitHub App with flat per-organization pricing (not per seat, so it doesn't line up against $20–$60/seat AI reviewers). GitHub Marketplace requires 100 installations before an App can list paid plans; that is the gate, not a goal. Paid features coordinate teams (accuracy dashboard, shared config, multi-repo, history caching); the core analysis stays free.

## 11. Version single source of truth

`package.json` and `src/version.ts` both carry the version string so the source tree can run directly without a code-generation pre-step. An automated test in `test/schema.test.ts` asserts `GUTTER_VERSION === package.json#version` on every test and release run, preventing drift.

## 12. Detached-HEAD release tags carry `dist/`

`dist/` stays in `.gitignore` on `main` so pull requests never carry build diffs. When a `vX.Y.Z` tag is pushed, `.github/workflows/release.yml` runs `npm ci`, typechecks, tests, builds `dist/`, force-adds `dist/` into a single detached-HEAD release commit, and moves both `vX.Y.Z` and the major `v0` tag to that commit. Consumers referencing `lbrodie11/gutter@v0` or `lbrodie11/gutter@v0.1.0` always get a prebuilt `dist/action/main.js` that runs on Node ≥ 22 without installing dependencies or stripping types at runtime.

## 13. Snapshot `SourceReader` and pure `assembleBrief` for zero-leakage replay (`GU-03`)

Historical PR replay (`gutter bench`, `replayBrief`) must never read the checked-out working tree, check out a commit, or fork Gutter's question-generation pipeline. All file and config reads in static analysis (`src/evidence/imports.ts`, `src/evidence/tests.ts`, `src/config.ts`) go through `SourceReader` (`src/source/reader.ts`), with `WorkingTreeReader` for normal CLI/Action runs and `GitTreeReader(sha)` (backed by `git ls-tree -r -z` and a single argument-vector `git cat-file --batch` worker) for snapshot replay. `buildBrief` and `replayBrief` share the pure `assembleBrief` pipeline, while `replayBrief` uses `repo-archaeology` ≥ 0.4.0's library API (`openRepository({ cwd, head, base })`) offline without any `npx` fallback. GU-09 and GU-14 reuse `SourceReader`, and GU-05 swaps import analysis for Repo Archaeology's resolver behind this same interface.

## 14. Two-policy observational benchmarking and unverified Gate A (`GU-03`)

`gutter bench` evaluates historical PRs under two separate policies (`production` with as-of `backtest()` calibration at or before `base`, and `ungated` labeled `"research: not product behavior"` everywhere) and compares against three matched as-of baselines (`popular`, `popular-near`, `recent`) computed strictly from `base` ancestry. Post-merge changes within `--window-days` are recorded as observational outcomes (`followedUp`, `notFollowedUp`, `censored`, `targetDeleted`, `targetRenamed`, `resolvedAtMerge`, `unscorable`), never as automatic proof of a true omission: whereas `repo-archaeology backtest` measures same-commit coupling (`6.8×` lift on Hono), a 7-day post-merge window on an active repo naturally favors central high-churn files (`recent` / `popular`) that accumulate unrelated edits across subsequent PRs (`0.23` follow-up proxy vs. `0.65` for `recent`, lift `×0.36` on Hono). Therefore, Gate A (`Question usefulness`) always prints `UNVERIFIED` until human review labels exist in GU-04. All three benchmark artifacts (`bench.json`, `bench.md`, `bench.html`) are rendered from a single schema-validated model (`schema/bench.schema.json`) so report numbers can never drift from `bench.json`.

## 15. Stage 0 before the corpus; blinded, source-tagged labels (`GU-04`)

Before building a 20-repo benchmark corpus, Gutter runs a cheap, preregistered go/no-go on one repository (Hono, [`docs/benchmark/STAGE0.md`](benchmark/STAGE0.md)). Three choices follow from it. First, every baseline is scored on the same stricter outcomes as Gutter (same-author follow-up, RA follow-up signal), and the strongest baseline is chosen per outcome, so Gutter is never compared on an outcome where a baseline was picked for a different one. Second, comparison labels are blinded: Gutter questions and baseline proposals render identically, item ids are opaque, and source, evidence, and outcome are revealed only after a label is recorded (honor-system blinding: the payload is encoded in the page, not encrypted). Labels record their `source`, the first (blind) label, and whether it changed after the reveal; decisions count only the blind first label, one per labeler and item, so a label changed after seeing the answer can never move a result. Third, salience is tuned only through opt-in config keys (`salienceFullMinSignals`, `salienceBreadthFull`) whose defaults reproduce the shipped rule; benchmarks propose default changes, they never make them. The labeling page is a single self-contained file rather than a server so labelers need nothing but a browser, and nothing about the repository leaves the machine.

## 16. Track records stay internal; the bench pins its analyzer version (`GU-28`)

Repo Archaeology 0.10.0 attaches a per-pair `trackRecord` to each `diff` suggestion. Gutter reads it through one validating adapter (`normalizeTrackRecord`), where any shape other than RA's three documented ones counts as "no track record", so a malformed or future shape can never satisfy a `fired` threshold. It flows into an opt-in checklist gate and into bench records, never into `gutter.json`: schema v1 is frozen, and whether reviewers should see track records is a product decision (GU-06). The benchmark pins `repo-archaeology` exactly (devDependency `0.10.0`), while the peer range stays `>=0.4.0` so users are not forced to upgrade. Every analyzer upgrade is reported as a per-PR delta against the previous run, so analyzer changes cannot be mistaken for a variant's effect.


## 17. Explain, don't predict (`GU-29`)

**Evidence.** Gutter's benchmark on hono ([`docs/benchmark/STAGE0.md`](benchmark/STAGE0.md), pinned `eb754bd`, 200 PRs):

- *Stage 0, preregistered rule: STOP.* When Gutter asked "should this PR also have changed `<file>`?", that file changed afterwards less often than a simple "recently busy files" guess predicted: any follow-up ×0.36; same-author follow-up ×0.42 (bootstrap CI 0.21–0.69); RA-signal follow-up ×0.42 (CI 0.14–0.91). Against "busy files in the same folder" it was level on every measure.
- *Stage 0b, option 2: INSUFFICIENT.* Of the 90 companion questions, 67 paired a file with its own test file, 11 were direct imports, 10 unknown and only 2 ghost wires, both `never_fired`. The stricter rule left zero questions, so it was not tested, not disproven.
- Full reports went to 40% of PRs (budget < 1/3). With the old question content, V2 (`salienceFullMinSignals: 2`) gave 12%.

This is evidence against this companion rule on this repository. It is not evidence that no omission rule could ever work.

**Decision.** Decided by the agent on the maintainer's explicit delegation, based on the evidence above and without the optional Stage 0 labels; the maintainer's merge of this PR is the approval.

- Gutter's default output stops making predictions about omissions. It reports facts: broken imports, test status, breadth and dependents.
- Co-change history stays as context, with receipts. It is never a question and never a reason for a louder page.
- The old behavior stays available, complete and reproducible, behind one research switch, along with a stated rule for bringing a better predictive rule back.

This is decision #1 ("we explain; others judge") applied to Gutter's own questions. The product promise becomes: Gutter shows what a PR changes, what depends on it, what the tests show and what the history says, with evidence for every line. You decide what matters.

**What changes by default.**

- The checklist holds only `broken-import`, `untested-change` and `wide-surface`. Co-change can neither create nor suppress an item, so the old `asked` suppression of `untested-change` is gone. `untested-change` is a statement: "`src/x.ts` changed (+12/−3); its test file `src/x.test.ts` didn't change in this PR." Its gate (`minChurnForTestQuestion`), single-item cap and priority 4 are unchanged.
- Test-pair history moves to the Tests panel as `TestLink.history` (`{ together, sourceCommits, evidence }`, additive): "`src/x.test.ts` — unchanged in this PR · changed together with `src/x.ts` in 17 of 20 commits", with receipts. It is built after the checklist and salience, from their output only, so it cannot change either. The counts describe the pair with the test the naming conventions found when that test is a co-change partner (so the Tests row and the checklist always name the same file), otherwise the strongest pair; each row cites only its own pair's commits. A test partner the conventions missed is added as a candidate, which can move a link from `no-test-found` to `test-untouched` in `gutter.json` without adding a checklist item. Rows without a pairing say whether history was checked, partial, too short or not checked, never a blank.
- `forgotten` keeps its name and data (required by v1) and gains `presentation: "context"`. The comic's C-04 becomes "Usually changes with", keeps its position (cut order unchanged) and is never the hero; the hero is C-06 "Check these" when it has items, otherwise C-03 "What it touches". The Markdown comment shows it as a collapsed `<details>` titled "Usually changes with (history, not a prediction)" on `full` and `brief` pages; `quiet` pages stay one line.
- **Salience.** `salienceFullMinSignals` defaults to 2. Each checklist item with priority ≤ 2 counts once and breadth (≥ 8 files or ≥ 3 modules, when `salienceBreadthFull` is true) counts once. By default only `broken-import` has priority ≤ 2, so a page is `full` when it has two or more broken-import items, or one broken import plus breadth. Breadth alone is never `full`. Any checklist item still makes a page at least `brief`, which is why test history stays out of the checklist. Co-change context and test history never contribute.
- User-facing wording ("forgot", "likely forgotten", "missing companion", "untested", "not covered") is gone from renderers, CLI output, the README, `action.yml` descriptions and docs. Code identifiers, the `forgotten` field, the `max-forgotten` input and `--max-forgotten` flag keep their names because they are part of the contract.

**What stays available.** `.gutter.json` / `--config` key `legacyPredictions: true` ("reproduces pre-GU-29 behavior for benchmarks; not recommended") runs the old checklist code path unchanged (companion and family-drift questions, the `asked` suppression, the old wording), defaults `salienceFullMinSignals` to 1 (an explicit value still wins) and omits `forgotten.presentation` and `TestLink.history`. `gutter.json` from the same inputs is byte-identical to the pre-GU-29 output apart from provenance version and timing (`test/gu29.test.ts`, eleven fixture goldens captured before the change), and on hono it reproduces Stage 0b's default run record for record. `maxCompanionQuestions`, `minIntervalLow`, `minCalibratedPrecision`, `companionRequireGhost` and `companionMinTrackRecordFired` apply only under `legacyPredictions`; setting one without it prints a warning (CLI and Action), and `gutter bench --config` refuses it so a preregistered variant can't silently run as a no-op (`gutter bench --legacy-predictions` turns the switch on for a run). `ChecklistKind` and the schema keep `forgotten-companion` and `family-drift` so v1 readers keep working. This entry supersedes the companion-question parts of #5 (interval floor and bot filter as question gates) and #6 (calibration gating questions) for the default output; both still hold under `legacyPredictions`.

**Reopen rule.** A predictive rule returns to default output only if, on ≥ 3 corpus repositories, a preregistered rule beats the strongest baseline (lift > ×1.00, with the bootstrap interval's lower bound > ×1.00) on same-author or RA-signal follow-up, with ≥ 30 scored targets per repository.

**Exit tests.** Gate A ("questions right ≥ 70%") no longer fits a product that asks no predictive questions. M0's exit test becomes Gate A′ in [`ROADMAP.md`](ROADMAP.md): quiet enough, facts true, no predictions, all checkable without human labels. Human usefulness is judged in M1. On hono, Gate A′ passes on what hono exercises (no `full` page; 10/10 `untested-change` and 43/43 test-history facts confirmed; no prediction wording on any of 200 pages), and `broken-import` is unexercised because no PR in the sample removed an imported file.

## 18. Repo Archaeology is loaded as a library, one session per brief (`GU-05`)

Repo Archaeology owns co-change statistics, commit-origin classification and import resolution (#2). Gutter now consumes all three from one in-process session instead of re-implementing parts of them.

- **Order of preference.** `repo-archaeology` stays an optional peer dependency (`>=0.4.0`, the first release with `openRepository` and the import resolver; 0.10.0 is the dev pin and the Action's default). Gutter loads it through one loader (`loadRaLibrary` in `src/sources/archaeology-lib.ts`; a test fails if a second import site appears) in this order: (1) the library (`--ra-lib` / `GUTTER_RA_LIB`, or the installed package); (2) a binary (`--ra-bin` / `GUTTER_RA_BIN`, the previous behavior); (3) `npx`, now a last resort that adds a note to `forgotten.note` and prints a warning; (4) "history unavailable". `--no-history` skips Repo Archaeology entirely: an offline static run.
- **One session.** `openRepository({ cwd, head, base })` loads history once; `diff`, `backtest` (unless calibration is off) and `importGraph` all read that session, which is closed in a `finally`. Because the session reads blobs at `head`, the old "history needs `head` checked out" skip no longer applies on the library path. The backtest is base-isolated, so the PR's own commits are no longer part of its held-out window (bench replay always worked this way).
- **"What it touches" from the import graph.** Importers come from reverse edges of `importGraph({ files: <changed files at head> })`. Deleted and renamed-away paths don't exist at head, so their importers come from the session's repo-wide `unresolved` entries whose relative specifier points at them (`target-missing`); they become broken-import candidates as before. `coverage` is `partial` when any other import in the repository is unresolved, because such a file could be an importer Gutter can't see (the scoped list alone would miss it). That repo-wide pass reuses the session's index, about a millisecond on hono. `dependents.unresolved.byReason` counts Repo Archaeology's `reasonCode`s, `dependents.analyzers` lists `ra-import-graph` and the edge `via` kinds seen, and `unchecked` lists changed files in languages the graph doesn't cover. The relative-import scanner (GU-02) is the fallback.
- **Statistics and origin.** A suggestion's `interval` replaces Gutter's own Wilson computation; evidence `origin` sets `CommitRef.automated` (`origin === 'bot'`) and is kept as `CommitRef.origin`; `originShare.bot` becomes `automationShare`, and `originShare` is kept. `src/stats/wilson.ts` and `src/evidence/automation.ts` remain only as fallbacks; the bot list is no longer maintained.
- **Provenance.** `provenance.engines[]` records `mode` (`library` / `subprocess` / `npx`) and `features` (the optional fields detected: `interval`, `origin`, `originShare`, `trackRecord`, `followUps`, `owners`, `importGraph`), so bench results are traceable to how Repo Archaeology ran.
- **Config boundary.** With `configRef` (the Action reads configuration from `base`), the session gets the base tree's validated `.repo-archaeology.json` as explicit settings with `useConfigFile: false`. Repo Archaeology's `ignore` rules shape the import graph, so reading the PR's own file would let a pull request hide its own broken import (found in review on PR #17). Locally, without `configRef`, the checked-out file is the user's own and still applies. In the subprocess fallback the Repo Archaeology CLI still reads the working tree's file, but there it only shapes co-change context, which never creates a checklist item or raises salience; dependents come from Gutter's scanner.
- **The Action never installs into the user's repository.** It runs `npm install --no-save --ignore-scripts --prefix <prefix> repo-archaeology@<archaeology-version>` from `RUNNER_TEMP` (so the PR checkout's `package.json` and `.npmrc` are never read), where `<prefix>` is `$RUNNER_TEMP/gutter-ra/<spec>-<checksum>`: one prefix per requested spec, so two steps asking for different versions never reuse or cache each other's install (also found in review). It caches that prefix with `actions/cache` keyed on the spec and passes it as `GUTTER_RA_LIB`. If the install fails, the brief falls back to `npx` with a notice. The default spec moves from `^0.4.0` to `^0.10.0`: in 0.x a caret range caps the minor version, so `^0.4.0` could never pick up `interval`, `origin` or track records.

**Cost.** One library session does more than the old two subprocesses did (it also builds the import graph), so a brief is not always faster: on the hono example the library path took about 1.1 s and the subprocess path about 0.8 s. The gain is one history load, dependents through aliases, workspaces and `exports`, and honest coverage. On hono, the resolver adds `wide-surface` to 3 of 200 PRs and still finds no `broken-import` ([`STAGE0.md`](benchmark/STAGE0.md#after-gu-05--repo-archaeologys-session-and-import-resolver-2026-11-10)). Under `legacyPredictions`, 68 PR records differ from Stage 0b only in a companion interval's fourth decimal (Repo Archaeology rounds outward), and every rate, lift and full share is unchanged.

## 19. Gate A′ is measured on a preregistered corpus, with seeded PRs for the facts real PRs never produce (`GU-30`)

Gate A′ (#17) asks whether Gutter is quiet, true and non-predictive on the median repository. Hono alone could not answer it: `broken-import`, the only fact that can make a page `full`, never fired in its 200 merged PRs. Merged PRs passed CI, so they almost never contain a broken import. Running more of them does not help.

- **Corpus by rule, preregistered.** Twenty repositories (hono for continuity; TypeScript libraries, apps with `paths` aliases, workspace monorepos, Go, Python, a very young and a generated-code repository) were chosen by a mechanical rule from saved GitHub search results, each pinned to a SHA, in a commit that precedes every result ([`CORPUS.md`](benchmark/CORPUS.md) §1–§5, checked by `test/gu30-prereg.test.ts`). Every skipped candidate is logged with its reason. No human approval step: the commit fixes the list.
- **Seeded mutations for truth.** Per repository, 30 positives (a file or Go package deleted or renamed, importers left untouched) and 30 negative controls (a rename with every importer updated, deleting an unimported file, a move with a re-export left behind, a test-only edit) are generated from a fixed seed and committed onto real PR heads with git plumbing. Gutter's replay then analyzes each synthetic PR.
- **Ground truth by module resolution, independent of Repo Archaeology.** TypeScript's own `resolveModuleName` (nearest tsconfig, workspace packages linked virtually), Go module paths and Python module names decide whether an importer is broken. Every generated case is verified by the oracle before use. Symbol-reference oracles were rejected because they overcount consumers (RA-18's preregistered pilot failed on exactly that).
- **Honest denominators.** Positives that Gutter skips as `unchecked` or `partial` stay in recall's denominator and are reported separately; they never count as hits. A criterion with no items is "not exercised", never "met".
- **Coverage on every PR.** Bench records gain optional `coverage`, `unresolvedByReason` and `uncheckedLanguages`, so coverage honesty is measured across all PRs, not one example.
- **The verdict is mechanical** (PASS, INCONCLUSIVE or FAIL, from §5), and no product default changes in the same PR. A FAIL produces ranked failure classes and, where a configuration lever exists, `bench/variants/*.json` proposals; changing a default needs its own prompt.

**Result (2026-11-10): FAIL.** All 20 repositories completed. Gutter is quiet (no `full` page in any repository) and never used prediction wording, and every `untested-change` and test-history fact was true. But on seeded removals it found 0.63 of broken imports (TS/JS 0.90, Go 0 of 81, Python 0 of 90) at precision 0.98: only relative TS/JS specifiers are mapped to removed files. M0 stays open; the next step is a follow-up prompt for that mapping and a fresh preregistered run.

## 20. Broken imports come from base and head import graphs, in every language Repo Archaeology resolves (`GU-31`)

GU-30 failed Gate A′ on recall: Gutter mapped a deleted or renamed-away path to its importers only through relative TS/JS specifiers (#18), so Go, Python, `paths` aliases, workspace packages and `exports` subpaths never produced a `broken-import` item, although Repo Archaeology resolves all of them. The base tree already knows who imported each removed path and with which specifier, so the question becomes: does that specifier still resolve at head?

- **Base graph only when something is removed.** For a PR that deletes or renames a file, Gutter opens a second Repo Archaeology session at the merge base (`base...head` diffs against it) with the head session's explicit settings, `useConfigFile: false` (the PR's config file never applies), `maxCommits: 1` and the history cache off: the import graph reads the tree, not history, so this is the cheapest session the API allows, and it never writes under `.git`. It reads `importGraph({ files: <removed paths> })`; Repo Archaeology indexes the whole base tree either way, and `files` only scopes the result to the removed files and their reverse importers. If one removed path cannot be scoped (a submodule), the session's unscoped graph is used. A PR that removes nothing opens no base session (tested with a spy).
- **The rule.** A base edge `e` (`from`, `to`, `specifier`, `kind`, `via`) into a removed path is a broken import when `e.from` still exists at head, the head analysis covered it, and `e.specifier` from `e.from` no longer resolves to what `e.to` was: no head edge from `e.from` with that specifier (any language), or, for Python only, the specifier now reaches only files it already reached at base (`from pkg import mod` falls back to `pkg/__init__.py` when `mod.py` is gone), unless the removed file is an `__init__.py` above the named module (`import a.b.c` still works without `a/__init__.py`). A new head target replaces the removed file, except an `__init__.py` on the specifier's own module path standing in for a removed submodule (`from . import mod` falls back to the importer's own package `__init__.py`); when the removed file was the named module itself (`a/b.py` for `from a.b import x`), its package form `a/b/__init__.py` does replace it. An index fallback, a Go package with other member files, a module moved into a package of the same name and a re-export left at the old path all still resolve, so they are not broken. An importer removed too is not broken; an importer the PR changed counts only while the head graph still lists that specifier as unresolved. A file the PR adds or changes, with no comparable base edge, is a changed importer when its import is unresolved at head and points at a removed path: relative specifiers by path, others when a base importer resolved the same specifier to that path (a tsconfig `paths` alias only within the same top-level directory; a specifier that reached two removed paths is skipped). An importer the head analysis said nothing about (no edge, no unresolved import) while its other base imports still exist was not really analyzed at head and is skipped. All four edge kinds count (`static`, which includes type-only imports, `dynamic`, `reexport`, `require`); unknown kinds are ignored and an unknown `via` uses the "still resolves" test.
- **Go reports packages.** A Go import names a package, so a removed package gives one item (its first removed file), not one per file.
- **Fallback and provenance.** Without the library, or when the base session fails, the relative scan is unchanged (GU-02 scanner, or #18's `target-missing` mapping on the head graph). `dependents.method` (additive, optional; schema v1) says which ran: `base-graph` or `relative-scan`. It is absent when the library ran and nothing was removed.
- **`coverage: partial` keeps its meaning.** Imports reported as broken are not counted, and, as before, neither is a relative specifier into a removed path. GU-30 found every PR `partial` at the median repository; scoping coverage per PR or per file is a separate follow-up.
- **Cost.** The base session runs alongside the head session's diff, backtest and graphs (built serially, it had added 55% to hono's p95 on PRs that remove files). It is still over the +50% p95 budget on most repositories: in Rerun 1, on the 235 real PRs that remove a file, replay p95 grew from −9% to +159% by repository (hono 696 → 1801 ms, `allianz/ng-aquila` 1663 → 3201 ms), because Repo Archaeology re-indexes the whole base tree. So, as GU-31 required, base graphs are cached per base tree within a bench run (seeded mutations share a host; at most 8 kept), and the product-path cost is documented: about 0.2–4 s more on a PR that deletes or renames a file, nothing on any other PR. Real-PR replays and the product path never cache, so the measured cost is the product's ([`README.md`](benchmark/README.md), per repository). The fix belongs in Repo Archaeology (RA-20: reuse the head session's analysis for unchanged files).
- **Not in Repo Archaeology.** The Python leaf/ancestor test re-derives part of Repo Archaeology's module walk from specifiers and paths. An edge field naming what each target satisfies (the module, an initializer on its path, an imported submodule) would make it exact; that belongs in a Repo Archaeology prompt, not here.

**Result (Rerun 1, 2026-11-11): PASS.** Same corpus, oracle (with erratum 2: an AST import walk and NUL-byte blobs, after GU-30's seven precision cases turned out to be oracle misses or outside its definition), quotas and rule, preregistered afresh with seed `20261111` before any data ([`CORPUS.md` §6](benchmark/CORPUS.md)).
